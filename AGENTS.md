## Цель V3 — мульти-стратегийный торговый агент

Поскольку ОДНА модель направления/относит. силы не нашлась, прибыльный агент = **портфель
слабо-коррелированных стратегийных сливов**, каждый с СВОЕЙ экономической причиной эджа, поверх —
общий риск-слой. Прибыль из агрегата и контроля риска; отдельные сделки/сливы могут быть в минусе.
Альфу ищем там, где НЕ искали: в **экзогенных причинах** (нефть/FX/события) и **бета-нейтральных
спредах** (пары), НЕ в новой геометрии тех же цен. Полностью — `docs/ARCHITECTURE_V3.md`.

Сливы: **S1** пары-статарбитраж (market-neutral) · **S2** макро-тилт экспортёры↔внутренние по
нефть×USDRUB · **S3** событийные новости (дивиденды/байбэк/сюрприз/санкции) · **S4** риск-управляемый
бета-кор (опц.). Статус очереди: **H9 (S3) задеплоен** — paper-shadow, forward-гейт копится; **H6
(макро) и H7 (пары) закрыты** (см. леджер); **H8** — резерв после прод-H9.

## Архитектура: блоки (V3)

```
                ┌─ свечи (12+ бумаг, мульти-TF) ───────────────┐
ДАННЫЕ          ├─ market context: Brent, USDRUB, RGBI, IMOEX ─┤
                └─ news ingestion (лента) ─────────────────────┘
                                   │
ПРИЗНАКИ   quant (цена/технички, кросс-секц. z) ⊕ макро-беты (нефть/FX) ⊕ LLM news-события
                                   │
СЛИВЫ      S1 pairs · S2 macro tilt · S3 event-driven · S4 risk-managed core
                                   │  ← КОМБИНАТОР (нетит позиции, веса по риску)
ПОРТФЕЛЬ   risk_manager: vol-targeting (H4) + режимный гейт (H5) + лимиты + кап корреляции
                                   │
ИСПОЛНЕНИЕ  execution (paper/dry-run, комиссия+проскальзывание)
                                   │
МОНИТОРИНГ  P&L-атрибуция ПО СЛИВАМ (слив без эджа на forward → вес 0)
```

Всё взаимодействие блоков — **только JSON**, валидируется схемами в `contracts/`.

**Собрано и задеплоено (весь стек — Python):** `backend/` (автономный ingest + integrity-гейт +
торговый календарь), `ml/` (сервинг H9/S3 + риск-аналитика H4/H5), `llm/` (самообновляемый
дивидендный фид), `risk_manager/` (комбинатор сливов + shadow-гейт), `execution/` (T-Invest, paper),
`agent/` (оркестратор + планировщик), `bot/` (Telegram-мониторинг), `infra/` (Docker/VDS).
**Удалён:** `aggregator/` (роль late-fusion 0.75/0.25 ушла в раннюю фьюжн) и **Go-бэкенд целиком**
(внутренняя агрегация из Go `decision_service.go` — теперь в Python).

## Контракты (`contracts/`)

Расширяем обратносовместимо (не ломая дисциплину JSON):
- `llm_analysis`: новостные **события** `{event_type, surprise_vs_expectation, affected_tickers[],
  impact_score, as_of, source}` (НЕ buy/hold/sell, НЕ просто sentiment).
- `feature_bundle`: `[quant ⊕ macro ⊕ news]` на вход сливов (добавить поля `macro_*`).
- `aggregated_signal`: целевые позиции **+ поле `sleeve`** (s1_pairs/s2_macro/s3_event/s4_core).
- `risk_analytics`: vol-прогноз + режим + сайзинг/лимиты для портфельного слоя (есть).

Вход ML (`candle_batch`) без изменений; ML-блок САМ подтягивает ортогональные данные при инференсе.
Схемы: `contracts/*.schema.json`; весь JSON I/O проходит валидацию (`scripts/validate_contracts.py`).

## Метод валидации (НЕ нарушать)

Валидировать **ТОЛЬКО deployment-симуляцией**: скользящий ретрейн сквозь СВЕЖИЙ forward-период,
с комиссией. Обычный walk-forward нас обманул. Критерий — устойчиво положительный результат на
forward, не пиковый Sharpe на одном куске. Робастность важнее пика.

## Инварианты (никогда не нарушать)

1. **Нет утечки теста**: тест-сплит не используется для тюнинга/отбора моделей. Тест 2025-2026 сожжён.
2. **Хронология**: фолды по времени, без перемешивания.
3. **Только прошлое**: фичи в момент t используют данные только из [t−window, t]. Для новостей —
   no-lookahead по времени ПУБЛИКАЦИИ, не события.
4. **is_production=false**: всегда на research-артефактах, до честного forward-гейта + sign-off.
5. **Валидация контрактов**: весь JSON I/O проходит схемы в `contracts/`.
6. **Смоук-тесты зелёные**: `python -m pytest ml/test_smoke.py` перед любым PR.
7. **Агрегация сидов**: гиперпараметры выбираем усреднением по сидам, не cherry-pick.
8. **Time-shuffle контроль**: forward IC фичи обязан ПАДАТЬ под перестановкой во времени, иначе это
   статический тикер-байас, не динамический сигнал. Любая новая фича проходит этот контроль.
9. **Гейт на каждый слив отдельно**: слив попадает в книгу только пройдя свой deployment-гейт; слив
   без эджа на forward → вес 0 (видно по P&L-атрибуции).
10. **Бета осознанно**: S1/S2 — конструктивно бета-нейтральны (относительное, не абсолютное); S4 —
    осознанная бета под управлением гейта. Книга в целом — контролируемая, не случайная бета.
