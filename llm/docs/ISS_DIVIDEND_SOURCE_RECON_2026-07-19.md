# Разведка (Stage 0): может ли бесплатный MOEX/ISS заменить браузерный скрейп e-disclosure?

**Дата:** 2026-07-19 · **Блок:** `llm/` · **Статус:** read-only разведка, кода не написано
**Вердикт: NO-GO — путь B закрыт.** Остаётся путь A (рефреш вне VDS + доставка CSV).
`is_production=false` на всех артефактах разведки.

## Вопрос

Рефреш forward-фида (`data/news/dividend_calendar_upcoming.csv`) требует Playwright, которого нет и
не должно быть на боевом VDS (961 МБ RAM) → рефреш в EOD-цикле падает
(`ModuleNotFoundError: playwright`), фид застыл на `as_of=2026-06-26`. Июльская волна в фиде есть,
осеннюю он не подхватит.

Проверялось: даёт ли какой-либо **бесплатный HTTP-эндпоинт** MOEX/ISS оба условия гейта решения,
зафиксированного ДО результатов:

- **(а)** forward record-даты, появляющиеся ≥ ~15 ТД ДО record (H9 входит на −12);
- **(б)** реальную дату объявления/появления как no-lookahead-якорь.

Путь B жизнеспособен **только если оба**. Провалено **оба** — и (б) проваливается структурно,
безотносительно к лагу.

## Кандидат 1 — `/iss/securities/{SECID}/dividends.json`

### (б) проваливается СТРУКТУРНО: в схеме нет даты объявления

Сырой ответ (`https://iss.moex.com/iss/securities/SBER/dividends.json`, HTTP 200):

```json
"columns": ["secid", "isin", "registryclosedate", "value", "currencyid"],
"data": [
    ["SBER", "RU0009029540", "2024-07-11", 33.3,  "RUB"],
    ["SBER", "RU0009029540", "2025-07-18", 34.84, "RUB"]
]
```

Пять полей, **ни одного временнóго якоря кроме самой record-даты**. Нет ни даты рекомендации СД, ни
даты ГОСА, ни даты появления строки в API. Единственный кандидат в якоря — `registryclosedate`, а это
ровно та скрытая утечка, которая запрещена: record-дата — это будущее относительно момента входа,
использовать её как «когда мы узнали» = отравить H9-гейт. **Даже идеально своевременный ISS этот
эндпоинт не спас бы** — no-lookahead на нём непроверяем в принципе.

### (а) проваливается эмпирически: лаг ~11 месяцев, опережение отрицательное

Решающий тест: в живом фиде есть июльские record-даты **по обе стороны от сегодня** (2026-07-19).

| ticker | record в фиде | vs today | есть в ISS? | последняя запись ISS |
|---|---|---|---|---|
| SIBN | 2026-07-06 | ПРОШЛА | **нет** | 2025-07-08 |
| MOEX | 2026-07-09 | ПРОШЛА | **нет** | 2025-07-10 |
| MTSS | 2026-07-09 | ПРОШЛА | **нет** | 2025-07-07 |
| ROSN | 2026-07-09 | ПРОШЛА | **нет** | 2025-07-20 |
| PLZL | 2026-07-13 | ПРОШЛА | **нет** | 2025-04-25 |
| TATN / TATNP | 2026-07-15 | ПРОШЛА | **нет** | 2025-06-02 |
| SNGS / SNGSP | 2026-07-16 | ПРОШЛА | **нет** | 2025-07-17 |
| SBER / SBERP | 2026-07-20 | БУДУЩЕЕ | **нет** | 2025-07-18 |
| VTBR | 2026-07-20 | БУДУЩЕЕ | **нет** | 2025-07-11 |

**Прошедшие record-даты в ISS: 0/9. Будущие: 0/3.** Эндпоинт не отстаёт на дни — он не показывает
даже события, record-дата которых прошла 13 дней назад.

Проверка «лагает или заморожен» — выборка 30 бумаг (наши 16 + префы + RTKM/RTKMP/BSPB/AFLT/FIVE/
UPRO/LSNGP/MTLR):

```
securities sampled with data : 29/30      (FIVE — 0 строк)
any 2026 record date anywhere: 0
global max registryclosedate : 2025-08-13
```

**Ноль записей 2026 по всей выборке**; глобальный максимум — 2025-08-13, т.е. ~11 месяцев
устаревания. Эндпоинт де-факто заморожен для цикла FY2025→2026, а не «догоняет с задержкой».
Подтверждает и уточняет то, что было известно с 2026-06-26 (тогда диапазон кончался 2025-07-20).

## Кандидат 2 — дивидендный календарь MOEX / ISS-бэкенд под ним

**Не существует в бесплатном ISS.** Каталог сервисов (`/iss/index.json`, `/iss.json`, 95 КБ:
engines / markets / boards) не содержит ни одного дивидендного или corporate-action сервиса — грep по
`divid|дивиденд|corporate|корпоратив|событ|event|action` даёт только «корпоративные облигации».

Пробы (все — HTTP 404, тело 14673 Б, стандартная заглушка ISS):

```
/iss/statistics/engines/stock/markets/shares/dividends.json   404
/iss/analyticalproducts/dividends/securities.json             404
/iss/statistics/engines/stock/dividends.json                  404
/iss/securities/SBER/corporateactions.json                    404
/iss/securities/SBER/events.json                              404
/iss/corporateactions.json                                    404
https://www.moex.com/api/dividends                            404
```

Страница `https://www.moex.com/ru/stocks/sber` (525 КБ) отдаётся полностью JS-рендерингом:
**0 упоминаний «дивиденд» в HTML и 0 извлекаемых api-путей** — то есть отдельного открытого
JSON-бэкенда, который можно дёрнуть из `requests`, за ней не стоит.

## Кандидат 3 — прочие corporate-action / event эндпоинты

Живые бесплатные ISS-сервисы рядом есть, но нужных данных не содержат:
`/iss/statistics/engines/stock/splits.json` (**только сплиты**), `/iss/securities/SBER/indices.json`
(членство в индексах), `/iss/securities/SBER/issuecapitalization.json`, `.../aggregates.json`,
`/iss/statistics/engines/stock/capitalization.json` (кстати, живой и свежий: `2026-07-19 13:09` —
т.е. ISS в целом работает и обновляется, мёртв именно дивидендный эндпоинт).

`/iss/datashop/algopack/...` отдаёт HTML-заглушку вместо JSON → **ALGOPACK платный, не берём**
(по условию задачи).
НРД (`nsddata.ru`) — authoritative-регистратор корпоративных действий — отвечает **HTTP 403**.

## Вердикт

**ISS не даёт опережающих дивидендов с якорем объявления → путь B закрыт.** Отрицательный результат
окончательный, а не «пока не нашли»: провал по (б) структурный (в схеме физически нет даты
объявления), поэтому его не исправит ни будущее обновление данных, ни более удачный парсинг.
Форсировать ISS в обход no-lookahead — значит завести скрытую утечку прямо в H9-гейт; не делаем.

**Остаётся путь A: рефреш вне VDS + доставка CSV.**

## Побочный результат, важный для пути A

Проверил заодно, нельзя ли просто выкинуть Playwright, оставив тот же источник. **Нельзя:**
e-disclosure отдаёт **HTTP 403 на все** plain-`requests` запросы — не challenge-страницу, а глухой
блок, включая корень сайта:

```
search API   : HTTP 403 len=1295   Forbidden / REQUEST-IP: ...
event page   : HTTP 403 len=1295
company page : HTTP 403 len=1295
root         : HTTP 403 len=1295
```

Значит браузер нужен именно как обход WAF, и «переписать на requests тот же источник» — не вариант.
Путь A должен держать Playwright там, где он есть (вне VDS), и доставлять на VDS готовый CSV.
