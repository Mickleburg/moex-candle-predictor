# Задача: bot — управляемый allowlist + admin-команды (runtime add/remove)

> Выдано лид-чатом 2026-06-22. Коммитить ТОЛЬКО `bot/` (+ свои тесты). Бот остаётся read-only по
> отношению к state-store агента (`mode=ro`) — но получает СВОЙ маленький стор для allowlist.

## Зачем
Сейчас whitelist статичен (`BOT_ALLOWED_CHAT_IDS` из env, читается на старте). Владельцу нужен
**простой способ из самого Telegram**: посмотреть список разрешённых, добавить/удалить пользователя,
без перезапуска и правки env. Доступ к боту — только у явно разрешённых; админ управляет списком.

Сейчас: админ `@turambar_e`, chat_id `5212870492`.

## Дизайн (придерживаться)
Два уровня доступа:
- **admin** — `BOT_ADMIN_CHAT_IDS` (env, bootstrap). Может всё + управлять allowlist. **Нельзя
  удалить через бота** (fail-safe: владелец не запрёт сам себя). Это «корень доверия».
- **allowed** — может вызывать read-команды. Эффективный allowed-набор =
  `admins ∪ BOT_ALLOWED_CHAT_IDS(env seed) ∪ managed-store`.

**Managed-store — СВОЙ файл бота**, не БД агента (её бот открывает `mode=ro`, писать туда нельзя):
`data/bot/allowlist.json` (gitignored — добавить `data/bot/` в `.gitignore`). Формат, например:
`{"5212870492": {"note": "turambar_e", "added_by": 5212870492, "added_at": "..."}}`. Запись —
атомарно (temp + `os.replace`). Отсутствие файла = пустой managed-набор (только env/admins).

`BotConfig.authorized(chat_id)` должен учитывать admins ∪ env-seed ∪ managed-store, причём
managed-набор читается ДИНАМИЧЕСКИ (перечитывать файл при изменении или держать в памяти и
обновлять при записи) — чтобы `/allow` действовал сразу, без рестарта.

## Команды (admin-only, кроме того что уже есть)
- `/users` — показать текущий allowlist: admins (помечены 👑, immutable), env-seed, managed (с note и
  кем добавлен). Только админ.
- `/allow <chat_id> [note]` — добавить в managed-store. Только админ. Валидировать, что id — int.
- `/deny <chat_id>` — удалить из managed-store. Только админ. **Отказать**, если id — admin или
  env-seed (их через бота не убрать; сказать почему).
- Неавторизованный пользователь, написавший боту: вместо молчания — короткий ответ «доступа нет,
  ваш id: `<chat_id>`, передайте администратору» + лог. (Опц.) уведомить админов одним sendMessage.
  Это превращает «как узнать свой id» в самообслуживание.

`/help` — дополнить admin-секцией (видна только админу).

## Дисциплина / приёмка
- Управляющие команды (`/allow /deny /users`) — строго `config.is_admin(chat_id)`; обычный allowed
  их не видит и не может вызвать (проверить тестом: allowed-не-админ получает отказ).
- Бот НЕ пишет в БД агента; пишет только в `data/bot/allowlist.json` (атомарно).
- `data/bot/` — в `.gitignore` (стор не коммитим).
- `.env.example` уже описывает `BOT_ADMIN_CHAT_IDS` (лид добавил) — синхронизируй имена с кодом.
- Тесты: новые юнит-тесты на (a) admin может add/remove, (b) удаление admin/env-seed запрещено,
  (c) добавленный id сразу authorized, (d) не-админ не может управлять. `pytest bot/` зелёный +
  `ml/test_smoke.py` 19/19. Лид перепроверит.

## Не делать
- Не добавлять торговых/kill-switch команд (бот остаётся монитором; это отдельный осознанный шаг).
- Не писать в state-store агента. Не коммитить ничего вне `bot/` (кроме строки в `.gitignore`).
